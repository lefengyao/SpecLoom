# SpecLoom 模型请求诊断日志设计

日期：2026-10-10  
状态：已批准并实施（SpecLoom 0.1.5）

## 背景

安装版曾出现“模型流接收数据时失败”错误。当前 `protocol-stream.ts` 只通过 `console.warn` 输出少量流错误字段；应用没有持久化日志管理器，`SessionRuns` 保存的也只有通用错误文案。应用关闭后，控制台信息不便找回，模型请求阶段、重试与最终失败也无法稳定关联。

## 目标

- 在用户再次复现时，能判断失败发生在请求发出、响应头、流读取、协议解析、重试还是结束阶段。
- 通过诊断编号，将会话里的错误与本机日志事件关联起来。
- 提供可查看、导出、清理的桌面日志管理界面，并限制日志占用。
- 日志不保存模型输入、输出或凭据，日志故障也不能覆盖模型调用原始错误。

## 不在本次范围

- 根据客户端日志推断供应商内部故障或保证确定远端根因。
- 保存模型提示词、回复、思考内容、工具调用参数、工具结果或原始网络响应。
- 遥测上传、远程日志服务、崩溃转储。
- 插件管理。插件管理是独立子项目，将在日志规格完成后另行设计；已确认范围包含 SpecLoom 内置插件和 Godot 项目插件。

## 方案比较与决定

1. **只增加控制台输出**：改动最少，但应用重启后信息难以找回，也没有保留和清理界面。
2. **只扩充会话错误字段**：错误附近可显示诊断信息，但缺少一个请求从开始、收到响应到重试的事件链，也无法记录不属于会话的应用级错误。
3. **主进程脱敏结构化日志与关键路径追踪（采用）**：日志独立于会话保存，以诊断编号关联模型请求事件；管理界面负责筛选、导出和清理。它能提供定位所需证据，并控制收集范围和容量。

## 设计

### 存储与生命周期

- 主进程新增诊断日志服务，使用 Electron `userData` 下的 `logs/` 目录，以 JSON Lines 保存版本化事件。每条记录包含 UTC 时间、事件 ID、事件类型、级别和可选诊断编号。
- 服务在应用生命周期内共享，由模型请求运行时注入。写入采用有序异步队列；流式响应的每个数据块不单独写日志。重要错误事件在返回错误前进入队列，日志写入失败时保留原始业务错误，并将日志故障降级到控制台。
- 启动时、追加新日志前和用户执行清理时应用保留策略：每个文件最多 5 MiB，日志总量最多 25 MiB，最多保留 30 天。超限或过期时先删除最旧文件；单文件达到上限时开启下一个滚动文件。
- 应用正常退出时等待日志队列排空，避免刚发生的失败事件随窗口关闭而丢失。

### 模型请求事件

围绕一次逻辑模型调用（包含其自动重试尝试）生成一个 UUID 诊断编号；每个底层尝试另有递增序号。该编号关联请求开始、连接失败、收到响应头、首个流数据、流读取失败、协议解析失败、计划重试、请求完成或最终失败等有限事件。每条记录可包含会话/运行标识、供应商 ID、模型 ID、协议、尝试序号、耗时、HTTP 状态、接收字节数与帧数、是否收到完成信号，以及规范化后的错误类别和安全错误码。

错误码只接受受限字符集并限制长度；不写入任意的底层错误消息。HTTP 只记录状态码和经过白名单处理的媒体类型，不记录响应头、完整 URL、域名、查询参数、请求体或响应体。重试事件与终止事件使用相同诊断编号，并说明当前重试序号及是否达到重试上限。

### 错误关联与界面

- 当模型请求最终失败时，会话记录在现有 `error` 字段旁保存可选的 `diagnosticId`，与通用错误文案一起展示；用户可以复制该编号用于查找日志。旧会话没有该字段时继续按原格式展示。
- 设置内新增“诊断日志”分区。列表展示时间、阶段、协议/模型标识、耗时、状态、重试序号和诊断编号；可按文本和诊断编号筛选，并展开查看该事件的允许字段。
- 支持导出受同一脱敏规则处理的 JSONL 文件，使用系统保存文件对话框选择位置；导出不包含用户输入或凭据。
- 支持删除过期日志和清空全部日志。清空全部前要求用户确认；清理操作不会触及会话记录、项目文件或其他应用数据。
- 界面展示当前日志大小、文件数及自动保留策略，便于用户判断何时清理或导出。

### 隐私边界

以下内容永不写入诊断日志或导出文件：提示词、模型回复、思考文本、工具参数和结果、API Key、认证/ Cookie 头、原始请求/响应体、完整端点、文件系统绝对路径及任意原始异常消息。日志字段使用显式白名单构造，不能把完整请求对象、错误对象或会话对象直接序列化。

## 组件边界

- **诊断日志服务**：主进程管理事件 schema、追加队列、文件轮转、保留、查询、导出、删除与退出前 flush。
- **模型追踪**：在 Agent 请求、协议流读取和重试路径发出生命周期事件；负责传递诊断编号，不负责文件存储。
- **桌面桥接**：通过受校验的 IPC 暴露日志摘要、筛选结果、导出和清理命令，不向 renderer 暴露任意文件路径或文件系统能力。
- **诊断日志视图**：提供本机日志浏览与维护操作，不改变模型请求流程。

## 失败处理

- 日志目录不可写、文件损坏或导出失败时，界面展示可理解的错误，模型请求仍按原逻辑运行。
- 日志服务捕获异常时，不以异常消息写回日志，避免递归故障和意外泄露。
- 查询只读取保留策略范围内的文件；损坏的 JSONL 行跳过并计入可见的读取问题，不让整页崩溃。
- 会话存储失败不应抹掉已经写入诊断文件的事件；诊断编号仍通过模型错误对象返回到可用的 UI 错误提示。

## 验收与测试

- 模拟 `reader.read()` 在收到部分数据后拒绝，能得到关联的请求开始、响应、错误、重试和最终结果事件；错误事件含诊断编号、阶段、计数和安全错误码。
- 模拟 HTTP 错误、idle timeout、协议错误与用户取消，事件类型彼此可区分，不将取消误报为流断连。
- 使用包含 API Key、URL 查询密钥、提示词和异常敏感文本的模拟错误，验证日志文件和导出文件不含这些值。
- 验证并发追加顺序、文件滚动、30 天保留和 25 MiB 总上限；磁盘写入失败时业务错误保持不变。
- 验证 renderer 只能经 IPC 查看和清理日志；诊断页面能按编号定位事件、导出文件和清理数据。
- 运行相关单元/集成测试、renderer 测试、全量类型检查及生产构建，确认打包版 `userData` 路径可用。

## 取舍与边界

此设计能精确描述客户端观测到的失败位置、请求阶段、重试行为和可见传输错误码。如果供应商网关主动关闭连接但没有返回可辨认的错误码，日志只能证明客户端在哪一步观察到断连；要确认远端内部原因仍需供应商侧记录。现有历史安装版没有保留足够事件，无法回溯补全；该能力从集成此设计后的版本开始生效。
