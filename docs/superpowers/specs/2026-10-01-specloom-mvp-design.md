# SpecLoom（织布机）MVP 设计

**日期：** 2026-10-01  
**状态：** 已确认，实施中  
**目标版本：** v0.1

## 1. 产品目标

SpecLoom 是面向 Godot 独立开发者的桌面智能体开发环境。它把大纲、设定、人物、地图、系统、任务、提示词、生成文件和验证记录组织成一个可追踪项目，让开发者可以用结构化规范约束智能体，减少工作区混乱、意外功能、超长脚本、节点布局失控和模块耦合。

首版以 Godot 4.x 为目标，支持用户配置的 OpenAI 兼容模型。桌面应用内置智能体，并通过本机 MCP 向外部智能体暴露同一套项目操作能力。

## 2. MVP 成功场景

用户选择一个 Godot 项目，初始化 SpecLoom 后：

1. 创建或导入项目大纲、实体和任务规范。
2. 确认本次任务的操作范围。
3. 让内置智能体读取规范和当前项目文件。
4. 智能体通过带版本令牌的工具或快照 Bash 生成一组项目变更。
5. 用户查看变更摘要和差异并批准提交。
6. SpecLoom 执行规范检查、引用检查和 Godot 无头验证。
7. 项目记录实体、任务、文件、版本、验证结果和决策原因。

成功状态是：生成物在任务范围内、版本检查通过、验证通过或明确报告失败原因，且旧上下文不能覆盖后来的人工作业。

## 3. 范围

### 3.1 首版包含

- Electron + TypeScript 桌面应用。
- 主进程中的 `ProjectCore`，作为项目文件和命令执行的唯一权威入口。
- Godot 项目选择、初始化、项目摘要和任务范围确认。
- Markdown 正文加 YAML front matter 的项目规范和实体文件。
- 内置智能体和 OpenAI 兼容模型配置。
- `read`、整文件 `write`、局部 `patch`、快照 `bash`、Skills 加载、Godot 验证工具。
- 本机 MCP 服务，复用 `ProjectCore` 工具契约。
- 版本门禁、变更差异、提交记录、冲突报告和验证记录。

### 3.2 首版不包含

- Unity、Unreal 或其他引擎适配。
- 云端协作、团队权限和插件市场。
- 对真实项目目录执行不受限的 Bash。
- 自动无提示合并冲突。
- 将任意旧记忆、缓存或模型上下文写回项目。
- 完整的既有项目反向工程和自动重构。

## 4. 项目文件布局

```text
<godot-project>/
  project.godot
  specs/
    project.md
    outline.md
    entities/
      characters/<id>.md
      maps/<id>.md
      systems/<id>.md
      items/<id>.md
      events/<id>.md
    tasks/<id>.md
    decisions/<id>.md
  .specloom/
    project.yaml
    generated-manifest.json
    history/
      changes/
      validations/
    skills/
      project-context/
      specification-reading/
      prompt-library/
      entity-catalog/
      entity-authoring/
      godot-generation/
      godot-validation/
```

`specs/` 是开发者可读、可手改的规范事实来源。每个实体一个文件，YAML front matter 至少包含 `id`、`type`、`status`、`version`、`relations` 和 `source`；正文保存叙述、约束和设计意图。

`.specloom/` 保存工具状态、生成映射、变更历史、验证结果和项目 Skills。缓存的 Skill 上下文必须记录引用文件及其版本令牌，不能替代 `specs/` 和实际项目文件。

## 5. 分层架构

```text
Renderer UI
   |
Electron IPC
   |
ProjectCore（唯一项目操作入口）
   |-- FileStore：路径限制、版本令牌、原子提交、历史记录
   |-- TaskScope：任务范围与权限
   |-- SkillRegistry：Skill 发现、加载和来源版本
   |-- AgentRuntime：OpenAI 兼容模型、工具调用循环
   |-- SnapshotRunner：临时快照、Bash 执行、变更收集
   |-- Validator：规范、引用、Godot 无头验证
   |
MCP Adapter（本机 Streamable HTTP）
```

UI、内置智能体和 MCP 不能直接访问项目文件系统。所有读写、局部修改、快照提交和验证均通过 `ProjectCore`。

## 6. 文件版本门禁

文件系统是唯一事实来源。智能体读取文件前必须取得当前版本令牌，读取必须绑定令牌。写入、局部修改、删除和重命名必须提交最近读取的版本令牌，并在提交时原子校验。

首版版本令牌使用文件内容 SHA-256，并对不存在的路径使用 `absent`。提交成功后记录新令牌、来源任务和操作者。新建文件只有在路径仍不存在时成功。

版本不匹配时，`ProjectCore` 拒绝操作并返回当前版本、冲突路径和可获取差异；智能体必须重新读取后重新规划。项目记忆、Skill 缓存和旧模型上下文不能绕过这个门禁。

多文件提交先在临时目录形成变更集，预检所有预期版本；任一路径过期则整批拒绝。核心串行处理自己管理的提交，逐文件再次校验，使用临时文件加替换，并记录提交日志和前后内容指纹。外部编辑器不遵守核心锁，因此普通文件系统无法保证跨路径或对外部写入的完全原子性；失败时按版本校验恢复已经写入的文件，遇到外部新修改则保留并报告恢复冲突。

## 7. 智能体工具契约

工具调用都由 `ProjectCore` 鉴权、校验任务范围并记录审计信息。

| 工具 | 作用 | 关键约束 |
| --- | --- | --- |
| `files.list_versions` | 获取路径存在状态、类型和版本令牌 | 路径必须位于项目根目录 |
| `files.read` | 读取文件 | 必须带匹配的 `expectedVersion` |
| `files.write` | 整文件写入或创建 | 更新必须带版本；创建要求 `absent` |
| `files.patch` | 局部修改 | 校验整文件版本和补丁上下文 |
| `bash.exec` | 在任务快照执行命令 | 不能直接写真实项目；有时限、输出上限和路径限制 |
| `skills.list` / `skills.load` | 发现和加载项目 Skills | 返回来源路径与版本令牌，不授予权限 |
| `godot.validate` | 运行规范和 Godot 验证 | 使用项目配置的无头命令和超时 |
| `changes.preview` / `changes.commit` | 查看或提交变更集 | 提交时重新校验全部版本 |

## 8. Bash 快照流程

任务批准后，`SnapshotRunner` 根据当前版本创建临时工作区。Bash 在 Linux Docker 容器中运行，唯一项目挂载是该快照；禁用网络，使用只读根文件系统，丢弃 capabilities，启用 no-new-privileges，并限制进程数、内存、CPU、执行时长和输出大小。Docker 或已配置镜像不可用时返回明确错误，不退回宿主 Shell。命令退出后，核心收集快照相对项目根的新增、修改和删除；重命名表示为删除加新建。

变更提交前，`FileStore` 重新获取所有受影响真实文件的版本，并与快照基线比较。全部匹配才生成待审差异；任一不匹配就拒绝整批提交并返回冲突。首版不允许 Bash 直接访问或修改真实项目路径。

## 9. Skills

Skill 是项目内可版本控制的流程和领域知识模块，不是额外的文件权限。首版内置以下 Skill 类型：

- `project-context`：项目结构、Godot 版本、命名和目录规则。
- `specification-reading`：项目宪法、规范目录、字段规则和任务约束的读取入口。
- `prompt-library`：项目提示词、角色提示词和生成模板的版本化读取入口。
- `entity-catalog`：人物、地图、系统、物品和事件实体的索引、关系和版本来源。
- `entity-authoring`：实体字段、关系、生命周期和 Markdown/YAML 约束。
- `godot-generation`：场景、资源、脚本生成边界和拆分规则。
- `godot-validation`：规范、引用、无头导入和场景冒烟验证流程。
- `task-planning`：任务拆解、范围确认、风险和完成标准。

每个 Skill 目录包含一个可读的 `SKILL.md` 和可选的结构化索引。规范、提示词和实体数据既可以由 Skill 提供读取入口，也必须保留在对应的事实文件中；Skill 不复制一份可独立变更的隐式事实。所有引用必须附带路径与版本令牌。加载时发现来源发生变化，应要求重新读取，不能继续使用旧缓存执行写入。

## 10. MCP

桌面应用启动本机 MCP 服务，内置智能体和外部客户端使用相同的 `ProjectCore` 工具。首版采用本机 Streamable HTTP，随机生成会话令牌，默认只监听回环地址；外部客户端必须显式提供项目会话和认证令牌。

MCP 不暴露任意文件系统或任意 Shell 能力，只暴露上述受约束工具。MCP 与桌面 UI 共享任务范围、版本检查、变更预览和提交记录。

## 11. 模型接入

用户配置 OpenAI 兼容的 `baseUrl`、模型名、API 密钥和请求参数。首版实现聊天消息、工具定义、工具调用、流式文本可选支持和错误重试上限；供应商差异封装在 `AgentRuntime`，不进入 `ProjectCore`。

API 密钥存储在操作系统凭据库；项目文件只保存非敏感模型配置。模型输出只能提出工具调用，工具的实际权限、路径和版本校验由核心执行。

## 12. 验证闭环

验证分三层：

1. **规范检查**：front matter 必填字段、ID 唯一性、类型值和文件布局。
2. **引用检查**：实体关系、任务输入、生成清单和项目路径必须指向存在且类型匹配的目标。
3. **Godot 检查**：在私有项目快照的隔离容器中运行配置的 Godot 4.x 无头导入/解析；若任务声明测试场景，则执行有时限的场景冒烟命令。Godot 导入可能执行项目脚本，不能直接退回宿主命令执行。后端或镜像不可用时明确记录未执行，不宣称验证通过。

每层返回结构化结果、命令、退出码、日志摘要、耗时和关联任务。失败不会被隐藏；默认阻止提交后的“完成”状态，但允许用户查看和修复失败变更。

## 13. 错误处理与恢复

- 版本冲突：拒绝操作，返回当前版本和差异入口，要求重读。
- 路径越界：拒绝操作并记录安全事件。
- Bash 超时或超出输出：终止命令，保留日志和快照，不提交变更。
- 模型超时、限流或无效工具参数：按有限次数重试，仍失败则保留会话状态并提示用户。
- Godot 验证失败：保留变更集和日志，状态标记为验证失败，不伪造成功。
- 应用异常退出：下次启动时清理过期快照，保留已提交历史和未提交任务草稿。

## 14. 测试与验收

- 单元测试：版本令牌、路径限制、补丁上下文、原子多文件提交和 Skill 来源版本检查。
- 集成测试：OpenAI 兼容工具调用、快照 Bash 变更收集、MCP 与桌面 UI 共用 `ProjectCore`。
- Godot fixture：最小 Godot 4 项目，覆盖创建实体、生成场景、引用检查和无头导入。
- 冲突测试：外部编辑一个文件后，旧令牌写入和快照整批提交都必须失败。
- 安全测试：Bash 不能写真实项目之外的路径，MCP 未认证请求被拒绝。

MVP 验收要求：用户可以从一个实体规范完成一次受控生成；能预览并提交变更；验证结果可追踪；旧版本写入被拒绝；桌面智能体与 MCP 结果一致。

## 15. 后续演进

后续可以把 `ProjectCore` 提取为独立本地项目服务，增加 stdio MCP 桥接、Git 提交/回滚、冲突可视化合并、既有项目反向建模和跨引擎适配。上述能力不改变首版“核心统一、版本先行、Skill 不授予权限”的边界。
